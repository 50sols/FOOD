# FOODEX V2 — OWNER-LOCKED ISOLATION & DELIVERY CONTRACT
Date: 2026-11-10 | Parent: #2503 | Integration: `Foodex_V2`

## Non-negotiable rules
1. **No V2 → main integration without a new explicit written owner instruction.** No main PR, cherry-pick, push, merge, tag, deployment, release or version promotion derived from V2 is authorized.
2. Every V2 Issue title MUST start with `V2`; create one issue-scoped implementation branch `feat/<issue>-...` or equivalent, and **base the PR on `Foodex_V2` only**. Before merging, verify `base.ref == Foodex_V2` and the latest exact-head required checks are GREEN. Any PR targeting `main` is invalid regardless of CI color.
3. `Foodex_V2` is an **owner-requested exception to ordinary issue-scoped branch naming**; only this permanent integration branch uses the exception. Do not create another V2 integration branch.
4. No direct feature commits to `Foodex_V2`; merge through reviewed PRs and preserve issue/PR/CI evidence. Do not use automatic merge, promotion or sync into main.
5. **Leaf coding completion (owner directive 2026-11-13, #2503 comment 6839665431):** Close a V2 implementation leaf as `CODE_COMPLETE / FINAL_ACCEPTANCE_DEFERRED` only once **all** source-required Backend/Dashboard/Customer/Driver/Van programming and applicable automated security, RBAC, localization and functional tests are implemented, its **issue-scoped** PR is merged **only into `Foodex_V2`**, and every required exact-final-HEAD CI check is GREEN. The closure comment must cite the merged PR, tested SHA, integration SHA, CI runs and remaining human/staging/live UAT or attestation tracked by #2503 or an existing gate. **A partial PR or merely green CI never makes an incomplete source requirement code-complete.** Final manual UAT and consolidated business acceptance occur at the end of V2 coding, not before leaf code closure. **#2503 stays OPEN** until all coding is complete and the final comprehensive acceptance/audit passes on the exact isolated HEAD; neither leaf closure nor CI authorizes `main` or production promotion.
6. Preserve current production behavior and tenant contracts: B2B=VAN ONLY, B2C=DRIVER ONLY, store-scoped RBAC, secure identity lifecycle, finance maker/checker, audit and invariants.
7. V2 implementations must classify API/route/permission/role/navigation/user-status/finance/dispatch changes for **Customer, Driver, Van individually**. Create a `V2 | MOBILE ...` Issue for each actual affected app and link it to the originating backend issue. A claimed no-impact requires written evidence and contract regression checks. Do not postpone API or mobile parity until merge to main.
8. UI routes must be server-authorized. Sidebar visibility MUST be a projection of true permission/tenant/module/entitlement/readiness decisions; no independent visibility security policy. Platform Owner does not evade authentication, tenant or financial hard constraints.
9. Arabic/English, RTL/LTR, accessible desktop/mobile web, tests, storage/queue/cache/notifications, failure paths and security reviews are required for impacted surfaces.
10. Laravel Setup ZIP & Admin Update ZIP: one-ZIP install, web installer, Super Admin updater, authenticated/signed source, SHA-256, backups, migrations and recovery; exact packages must pass fresh-install and supported-upgrade MySQL CI. All three Android apps must build from same final V2 SHA. Produce **isolated staging artifacts**, never publish production tags or install on live cPanel without owner release order.
11. If a workflow, branch protection or repository settings allow a main merge, this **does not constitute owner authorization**. A dedicated GitHub ruleset requiring owner approval for `Foodex_V2` → `main` must be configured separately by a maintainer; a branch-contained workflow alone cannot fully enforce a main-base server-side ban.
12. No direct changes to original main policies or production artifacts to establish this V2 program.


## Owner-authorized V2 single-account technical review policy (2026-11-14; #3615; #2503 comment 6883437456)

**Operating model:** FOODEX V2 is maintained through one owner-controlled GitHub account and one or more engineering/AI workers. A second GitHub identity is **not** an inherent source-code completion requirement. This owner instruction supersedes the prior internal blanket demand for an independent GitHub `APPROVED` review on HIGH-risk V2 leaves. It does **not** claim that a same-account technical review is an independent GitHub review, waive actual GitHub rulesets, or authorize V2 integration to `main`.

### Mandatory risk-classified review on each existing issue-scoped PR

- **LOW:** isolated text, presentation, accessibility or provably read-only changes with unchanged authorization, tenant scope, sensitive-data disclosure, persistence, business formulas and app/API contracts. Document impact/negative checks and `REVIEW_RISK: LOW`. Source review may be recorded as `TECHNICAL_REVIEW: RECORDED` or `FINAL_AUDIT: DEFERRED_TO_V2`; no second account is required by this repository policy.
- **HIGH:** authentication/identity, RBAC, tenant isolation, privacy, money/finance, dispatch/fulfillment, Customer/Driver/Van security-relevant API contracts, schema/migrations, Setup/Update ZIP, backup/recovery, cryptographic provenance, benchmark baselines, CI, governance, and repository automation. Before integration, record `REVIEW_RISK: HIGH`, a detailed **file-by-file technical review** (correctness, scope, abuse/rollback and failure modes), applicable security/tenant/negative tests, exact-head CI and any independent reproducibility/provenance artifacts. Review may be authored through the *same GitHub account* but MUST be described as an engineering audit, not as independent peer approval. A separate GitHub `APPROVED` review is not a repository-imposed requirement unless an external contract or actual GitHub protection expressly requires it.
- **UNKNOWN / mixed:** treat as HIGH until evidence narrows scope. A reviewer or implementer cannot downgrade risk to avoid tests, required approval, or genuine human/device/staging evidence. For high-risk changes, review and code changes should be distinct documented steps, and all identified blockers must be resolved before merge.

### One-account gate: implement → verify → audit → integrate

1. Use the **original** issue, branch and PR, with base exactly `Foodex_V2` and lease/file ownership verified. Never directly push feature code to `Foodex_V2`, merge V2 to `main`, tag, release or deploy without separate explicit owner authorization.
2. Finish all implementation required by the source Issue and affected Backend/Dashboard/Customer/Driver/Van contracts. Record affected/not-affected impact for all three mobile apps. Verify applicable Laravel, Flutter, security, cross-store/RBAC, AR/EN, migration, installer/update ZIP and recovery tests. Every applicable required GitHub check (including Repository Policy, V2 Isolation, terminal Required CI and special workflows) must be **SUCCESS on the exact final HEAD**; no red, missing, cancelled, pending or superseded check passes.
3. Record a PR audit with `TECHNICAL_REVIEW: PASS|FAIL`, `REVIEW_RISK`, reviewed paths, relevant threat/failure scenarios, test run URLs/commit SHA and open limitations. Same-account GitHub `COMMENTED` reviews are valid *audit records*, **not** independent GitHub `APPROVED` reviews. A review marked FAIL or an unresolved blocking finding prohibits merge. Automated and AI analysis are supporting evidence, not proof of independent human review.
4. For `gate:approval` / `gate:human` issues, **classify the underlying obligation**, not just the label: an outdated *internal second-account reviewer requirement* may be discharged through this recorded one-account technical/audit gate once this policy is merged; an actual GitHub required approval, specific owner acceptance, provenance/security failure, regulated requirement, device/staging UAT or irreversible data/release decision remains binding until its own evidence exists. Do not silently remove labels or equate a worker comment with explicit owner sign-off. A specific outstanding requirement in an Issue must be reconciled and documented before it is considered satisfied.
5. Respect actual GitHub branch protection, CODEOWNERS/rulesets and required reviewers. If GitHub server-side policy truly requires a second reviewer, do not self-approve, create fake identities or admin-bypass; an authorized owner must explicitly update that repository setting through the proper administrative control and verify it before one-account merge. This Markdown file alone does not change GitHub rules. Never relax required CI or branch isolation.
6. Immediately before merging, re-check latest branch refs, source completeness, no conflicting lease, risk audit and all exact-head required checks. Merge only into `Foodex_V2` by issue-scoped PR and record merged integration SHA. Close **only** implementation leaves that satisfy Rule 5 as `CODE_COMPLETE / FINAL_ACCEPTANCE_DEFERRED` with PR, SHA, CI and pending non-code acceptance details. A green CI run alone is not a completed issue.
7. Keep master #2503 open, maintain final V2 security/technical audit and remaining manual/device/staging/business acceptance register; correct defects before V2-wide final acceptance. A documented one-account engineering audit is transparent about its independence limits. No change to `main` or production is authorized by this policy.

**Mobile impact (Customer / Driver / Van):** This governance-only change does not change code, routes, permissions, APIs, screens or binaries in any of the three applications. Future app-affecting PRs still need their per-app impact classification and regression evidence.

**Security invariant:** One-account operation changes **who records the review**, not the required quality level, benchmark comparability, source provenance, tenant/RBAC isolation, secrets protection, signed update verification, backup/recovery safety or required CI. Do not weaken any technical or contractual gate to obtain a green status.

## V2 worker lease TTL — automatically released after 30 minutes without work

- Every V2 worker MUST claim an unowned Issue using a fresh public Issue comment with `<!-- foodex-worker-state:v1 -->` and fields `STATE: ACTIVE`, `OWNER: <github-login>`, `BRANCH: <existing issue branch or planned issue-scoped name>`, `HEARTBEAT: <UTC ISO 8601>`. Add label **`worker:active`** as part of the claim; this label makes the Issue eligible for the fast V2 sweeper. Verify no other valid claim or overlapping file-owner exists immediately before posting.
- A **30-minute idle TTL** is measured from the claim or the most recent independently verifiable commit on the owned branch/PR. **Comments, idle status pings, and self-declared heartbeat updates alone do NOT prove work** and do not reset the 30-minute clock. An active exact-head CI run keeps the lease safe while the CI job is genuinely running. Explicit production/human blockers must not be mistaken for permission to deploy.
- When 30 minutes elapse without verified activity, V2 watchdog removes active/waiting labels, assigns **`worker:handoff-ready`**, records a release comment, and makes the Issue free for another worker to claim. The original branch and PR remain intact: successor MUST continue them rather than creating duplicates.
- A worker who returns after an automatic release must stop until they revalidate ownership; if another worker has claimed the Issue, they must hand over. A superseding claim always wins.
- **Operational activation:** staged code `.github/scripts/v2-lease-watchdog.js` and workflow `.github/workflows/v2-idle-lease-watchdog.yml` request a sweep every **5 minutes**. GitHub only runs scheduled workflows defined on the **default branch**. Since owner has expressly forbidden modifying/promotion to `main`, this scheduled watcher is NOT YET AUTOMATICALLY RUNNING and must not be described as enabled. Future approval of a narrowly scoped default-branch dispatcher or a separate external 5-minute runner is required to enable unattended execution; no V2 feature changes may go to main under the present authority.
- The general repository watchdog on `main` runs hourly and its behavior is not an exact 30-minute V2 lease-enforcement guarantee. Until V2 watcher activation, workers must also manually revalidate leases before taking over and before every meaningful push/PR.


## OWNER DIRECTIVE — V2 FEATURE FREEZE AND BRANCH CLOSURE (2026-11-15)

**Effective immediately. This directive supersedes any earlier permission to start new V2 features or create additional implementation lanes.**

1. **FEATURE FREEZE:** No new feature development, feature Issues, scope expansion, new Sidebar destinations or speculative enhancements. Workers may implement only the outstanding acceptance criteria of already-existing V2 Issues and the defects, tests, security, CI, migrations, release-install/update verification and recovery work strictly necessary to finish those commitments. Any truly new scope requires a separate explicit written owner authorization; do not relabel a feature as a fix to bypass the freeze.
2. **CLOSE EXISTING WORK FIRST:** Inventory every existing temporary branch and open PR, reconcile Issue/owner/lease/head, and prioritize finishing existing branches to verified closure. For each: finish the original scope, run required checks on exact final HEAD, record review, merge into `Foodex_V2` only if fully accepted, close completed Issue and delete merged remote branch. Branches already merged may be deleted after verifying ancestry and no remaining PR/dependency. Never delete unmerged unique work merely to satisfy the cap; preserve evidence and record blockers. Abandoned/redundant branches require a verified disposition and owner-approved disposal of unique unmerged work.
3. **HARD CAP: `MAX_OPEN_V2_WORK_BRANCHES=12` and `MAX_ACTIVE_V2_WORKERS=12`.** Count all V2 temporary implementation/fix/test/chore/CI branches, including idle and waiting-CI branches, not merely active leases. Exclude only permanent protected integration/default branches (`Foodex_V2`, `main`) and unrelated historical protected release branches. One worker may own at most one open work branch and one active Issue/PR. A coordinator without a work branch may use a worker slot but cannot create a thirteenth work branch.
4. **OVER-CAP DRAIN MODE:** The existing inventory may exceed 12 at the time this rule is adopted. This is a backlog to reduce, **not** permission to create new work branches. Until the count is below 12, prohibit all new temporary V2 branches, including replacement/retry branches; workers must finish/take over existing branches and PRs. Once below 12, admit a new branch only if there is both a verified free branch slot and free worker slot, no existing branch for the Issue, no conflicting lease, and an explicitly permitted non-feature completion task. Re-check atomically immediately before creation. A one-time governance PR branch used to enact this directive must be merged/deleted promptly and is not a precedent for additional branches.
5. **NO FALSE CLOSURE:** Do not close incomplete Issues, merge red/missing/pending CI, delete branches with unmerged required changes, bypass review or force-push away work to hit a numeric target. Keep blocked work visible with exact reason, responsible owner and recovery plan. Red CI is a reason to fix the existing branch, not to abandon it.
6. **ISOLATION:** All V2 PRs target `Foodex_V2` exclusively. No merge/push to `main`, release, tag, production deployment or production promotion without a new explicit written owner approval. This freeze does not waive security, AR/EN, RBAC, tenant, Laravel/Flutter, signed ZIP, backup/recovery or exact-head acceptance gates.
7. **ENFORCEMENT AND REPORTING:** Before every claim/branch creation, count GitHub branches and worker leases, reconcile open PRs, and fail closed on uncertainty. Track `open_v2_work_branches`, `active_v2_workers`, `merged_and_deleted`, `blocked`, and `remaining_to_12` in coordination reports. A Markdown rule is an operating contract, not proof of server-side enforcement; add/test an automated admission gate separately without weakening the freeze.
