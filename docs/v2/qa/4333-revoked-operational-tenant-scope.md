# V2 #4333 — persisted revocation in OperationalTenantScope

- Parent: #2782 (P031), master #2503. Base: `Foodex_V2` only.
- A previously loaded User with `is_active=true` can become revoked in the persisted `users` row; checking only the Eloquent attribute is not authoritative.
- `allowedStoreIds` checks persisted `users.is_active` **inside each existing store-candidate SQL query**, including SUPER_ADMIN cross-join, scoped `user_store_roles` join, per-user STORE ALLOW join, and global-role store query. This avoids a separate per-call database query and retains existing query-count budgets. Revoked actors receive no store candidates; `assertStore` returns 404. No grant, impersonation, role/channel/override or mutation behavior changes.
- Test `V2RevokedOperationalTenantScopeTest` uses seeded reference roles, real Retail store records and DB revocation with intentionally stale User instances. Covers privileged and store-assigned actor, fresh revoked actor, reactivation, selected Retail, and unchanged audit rows for the Super Admin path.
- CI rescue: first implementation added one standalone persisted-active lookup and caused three existing query-budget tests to fail by exactly +1. Corrected in commit `ffb9dead` by embedding persisted-active checks into existing queries instead of increasing budgets. Security risk: HIGH; source and tests require exact final-head Repository Policy, V2 Isolation, Required CI including Laravel/MySQL/Redis and technical review before merge. Source-only evidence is not a claim of CI success.
- Mobile impact: Customer NO_DIRECT_IMPACT; Driver NO_DIRECT_IMPACT; Van NO_DIRECT_IMPACT. No Flutter/mobile source or API contract changes. No release, main or production deployment.
